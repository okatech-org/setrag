agent-web — portail de vente & portail de gestion

L'application interne du système billettique : le remplaçant de MOBIPASS. Une seule application Next.js, deux espaces conformes au CDC billettique — le portail de vente (guichets des 22 gares et agences accréditées) et le portail de gestion (administration fonctionnelle, comptabilité, pilotage). Next.js 16, design Cadence, port 3001.

Next.js 16 SSO Active Directory Rôles internes uniquement → plan backend

1Mission & utilisateurs

Tout le personnel passe par cette application ; ce que chacun voit dépend de sa matrice de droits (consultation / modification / suppression / validation).

2Authentification

  • SSO OIDC sur l'annuaire ERAMET (Entra ID / AD) — connexion < 2 s exigée par le CDC ; rôles dérivés des groupes AD ; déprovisionnement automatique (compte AD désactivé = accès coupé à la prochaine validation de session, sessions courtes de 8-12 h).
  • Repli provisionné en phases 0-1, avant l'app registration ERAMET : comptes internes créés par l'admin, MFA TOTP — bascule SSO sans toucher au modèle de rôles.
  • Chaque session est rattachée à un point de vente et à un appareil émetteur — champs obligatoires de chaque vente.

3Portail de vente

Objectif chiffré : émettre un billet en moins de 4 secondes. L'écran de vente est conçu clavier d'abord, champs minimaux, impression immédiate.

Vente billet — desserte, gares départ/arrivée (distance et prix calculés), classe, voyageurs (nom, prénom, sexe, téléphone, contact d'urgence), réductions applicables, place attribuée automatiquement ou choisie sur plan de voiture inventory.availability · fares.quote · sales.createTicketSale
Vente bagage — rattachement au billet, poids, frais d'enregistrement + excédents, étiquette imprimée baggages.create
Vente colis express — expéditeur/destinataire + téléphones, articles avec vignettes, grille zones × poids parcels.create
Vente TAA / transport funéraire — formulaires dédiés, codes tarifaires propres vehicles.create · funeral.create
Encaissement — espèces (rendu monnaie), mobile money (push USSD), client en compte ; proforma imprimable avant encaissement payments.initiate · sales.issueProforma
Annulation / remboursement — recherche du titre, motif paramétré, pénalité calculée, écriture liée jamais destructive sales.cancel · sales.refund
Duplicata — réimpression tracée, mention DUPLICATA portée sur le titre tickets.reprint
Ma caisse — ouverture (fond de caisse), état en cours par mode de paiement, clôture avec comptage et écart cash.openSession · cash.closeSession
Ressaisie des ventes manuelles — saisie des billets pré-imprimés du mode dégradé, numéro pré-imprimé + numéro système, continuité de séquence sales.recordManualSale
Résilience aux coupures (électricité, réseau) L'état de la vente en cours vit en local (brouillon persistant) : une coupure ne perd jamais une saisie. Si le backend est injoignable, l'écran bascule explicitement en consigne « mode dégradé papier » — les billets pré-imprimés prennent le relais, ressaisis ensuite. Aucune vente électronique n'est émise sans transaction confirmée.

5Exigences non fonctionnelles

  • Full web multi-périphériques (desktop, laptop, tablette) — navigateurs récents ; l'écran de vente est optimisé pour le clavier et les lecteurs de code-barres USB.
  • Émission billet < 4 s : quote tarifaire et disponibilité pré-chargées de manière réactive, impression asynchrone, une seule mutation de vente.
  • Traçabilité : toute action porte l'utilisateur, le point de vente et l'appareil émetteur ; les consultations de données voyageurs sont elles-mêmes auditées.
  • Anonymisation en environnement de test (exigence RGPD du CDC) : les jeux de données de recette sont générés, jamais copiés de la production.
